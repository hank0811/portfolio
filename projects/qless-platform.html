Web Development — Case Study

QLess — Campus Pre-Order Web App

The QLess ordering flow started as a Figma prototype. This is what happened when it got built out as an actual web app — menu, cart, slot booking and OTP pickup, running in the browser with no framework and no backend to hide behind.

RoleFrontend Developer
TypeClient-side web app
StackVanilla JS + CSS
StatusWorking demo

01 — Overview

From click-through to click-able

A Figma prototype can hide a lot of assumptions — every screen looks reachable, every state looks handled, because someone drew it that way. Building QLess as a real web app was about finding out whether the pre-order flow designed in the QLess UX case study actually held up once it had to run on real state, real input and real edge cases instead of pre-wired hotspots.

The scope stayed deliberately tight: no server, no database, no login system — just the core ordering loop a single-shop canteen actually needs, built to run entirely in the browser. Menu, cart, slot booking and OTP pickup all had to work off nothing but JavaScript state and the DOM, which meant every interaction had to be handled honestly instead of faked with a static mockup.

02 — How it's built

Three moving parts, one shared state object

Menu & cart

A plain JS object keyed by item ID tracks quantities. Every add, remove or quantity change re-renders the menu list and the sticky cart bar from that single source of truth — no separate DOM state to fall out of sync.

Slot capacity

Pickup slots are modelled with a fixed capacity per slot, not an unlimited list of times. Once a slot fills up it's shown as full and becomes unselectable — the zero-queue promise only means anything if slots can actually run out.

OTP pickup

Confirming an order generates a random 4-digit code and starts a live countdown, the same collect-by-code pattern from the original design, rebuilt here as an actual timer rather than a static screenshot of one.

The whole flow — menu, cart, slot picker, simulated payment, OTP confirmation — is one HTML file with view-switching handled by toggling a single active class, so the app never reloads the page as the customer moves through checkout.

05 — Learnings

01

A working build finds what a mockup hides

The design case study's "guaranteed pickup" promise only became a real engineering problem once slots needed actual capacity limits — a prototype can't run out of anything, an app has to decide what happens when it does.

02

State management doesn't need a framework at this scale

A single cart object and a handful of render functions were enough to keep five views in sync — reaching for React here would have added ceremony without solving a problem that existed.

03

Constraints make a demo feel true

Capping slot capacity and running a real countdown timer, instead of leaving both unlimited, is what makes the zero-queue pitch believable even in a backend-free prototype.
